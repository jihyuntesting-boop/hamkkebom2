## 3. 자동화: GitHub Actions(설정 기반)와 Python의 조합

학습 목표의 "노코드 자동화 도구와 Python 조합"에 대해 사실대로 적습니다.

- **노코드 도구는 쓰지 않았습니다.** 저장소에서 n8n, Zapier, Make 등의 설정·사용 흔적을 찾지 못했습니다(2026-11-26 저장소 전체 검색).
- 대신 코드를 짜지 않고 YAML 설정만으로 "언제, 어떤 조건에서, 무엇을 실행할지"를 정하는 GitHub Actions를 자동화 틀로 쓰고, 실제 데이터 처리는 Python 스크립트가 맡도록 나눴습니다.

## 4. 협업 방식

### 4.1 브랜치·PR·CI

- 작업 하나당 브랜치 하나(`claude/*`, `codex/*`, `feat/*`, `fix/*`, `docs/*`)를 최신 main에서 만들고, main에는 PR 병합(merge commit)으로만 반영했습니다. force push는 하지 않습니다.
- PR 전에 로컬 검사 7종(정본 문서 검사, 번들 일치, 원본 분리 동등성, 웹 스냅샷, API 계약, 번들 문법, 단위 회귀)을 실행하고, PR 본문에 실행 결과·확인하지 못한 것·되돌리는 방법을 적었습니다.
- 여러 PR의 병합 순서가 정해져 있으면 앞 PR 병합 뒤 최신 main을 merge해 다시 검사했습니다.
- 작업 기록은 저장소의 `STATUS.md`에 브랜치별로 남겼습니다(공개 스냅샷에는 포함하지 않음).
- 상세 규칙: [GIT_WORKFLOW.md](GIT_WORKFLOW.md).

### 4.2 AI 코딩 에이전트 활용과 사람 검토

- 개발 과정에서 AI 코딩 에이전트(Anthropic Claude, OpenAI Codex)를 활용했습니다. 에이전트는 작업 브랜치에서 코드와 문서를 작성하고 PR을 열었습니다.
- 팀장(개발·통합)이 작업 범위를 지시하고, PR 검토와 CI·로컬 검사 결과 확인 후 병합했습니다. 에이전트에게는 PR까지만 만들고 병합·force push는 하지 않도록 지시했고, 권한 없는 자동 배포·프로덕션 변경 금지는 작업 규칙(`AGENTS.md`)에 적었습니다.
- 화면 문구·표시 범위처럼 판단이 필요한 것은 "사용자 결정"으로 기록한 뒤 반영했습니다(예: 안전 보장처럼 읽히는 문구 비노출).
- 에이전트가 만든 변경도 팀장 계정의 커밋으로 기록되어 있습니다([CONTRIBUTORS.md](CONTRIBUTORS.md) §2).
