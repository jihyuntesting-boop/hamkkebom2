## 2. 프런트엔드: 바닐라 JavaScript 정적 앱

**선택 이유**

- 시작점이 하나의 HTML 파일에 CSS·JS가 들어 있던 기존 앱이었습니다. 프레임워크로 다시 쓰지 않고 CSS·JS를 원본 파일로 나누고(#2), 핵심 JS를 기능별 6개 원본으로 쪼갠 뒤 이어 붙여 번들을 만드는 방식(#5)을 택해 기존 동작을 유지하며 구조만 정리했습니다.
- 배포 폴더(`web/`)에 `package.json`이 없어 런타임 의존성이 0입니다. 공급망 점검 대상이 적고, Vercel에서 빌드 단계 없이 정적 파일로 배포됩니다.
- 번들은 `scripts/build_core_modules.py --check`로 원본과 바이트 단위 일치를 검사하므로, 빌드 도구 없이도 재현 가능한 빌드(NFR-06)를 지킬 수 있습니다.
- 시니어 접근성(큰 글씨, 44px 이상 터치 목표, 확대)은 프레임워크보다 마크업과 CSS 규칙이 결정한다고 보았습니다.

**대안과 고르지 않은 이유**

| 대안 | 고르지 않은 이유 |
| --- | --- |
| React·Vue 등 SPA 프레임워크 | 기존 단일 HTML 앱을 다시 써야 하고, 빌드 체인과 의존성이 늘어남 |
| Next.js(서버 렌더링) | 서버리스 API만 필요했고 페이지 렌더링을 서버에 둘 필요가 없었음 |

**한계**: 6개 원본이 한 스크립트 범위를 공유해 모듈 경계가 약합니다. 큰 기능을 더할수록 이 구조의 유지비가 커집니다.

## 3. 서버: Vercel 서버리스 함수

**선택 이유**

- 공공데이터·네이버·Anthropic 키를 브라우저에 두지 않으려면 서버가 필요했고, 상시 서버를 운영하지 않아도 되는 서버리스를 택했습니다.
- 정적 화면과 `/api/*`를 같은 출처로 배포해 CORS 설정이 필요 없습니다.
- API 핸들러(`web/api/*.js`)는 한두 줄로 서버 모듈(`web/server/*.cjs`)을 부르고, 검증·정규화·캐시·오류 분류는 서버 모듈에 모아 Node 내장 테스트 러너로 바로 시험합니다.
- 여러 Vercel 프로젝트로 나뉘어 있던 장소·날씨·접근성·사진 API를 하나의 프로젝트로 합쳤습니다(#56, #86).

**대안과 고르지 않은 이유**

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 상시 Node 서버(Express 등) + 별도 호스팅 | 서버 운영·보안 패치 부담 |
| 다른 서버리스(AWS Lambda 등) | 정적 배포와 API를 한 곳에서 관리하는 Vercel 구성이 이미 운영 중이었음 |

**한계**: 호출 제한·캐시가 인스턴스 단위라 최선 노력 수준입니다. 서버 DB·로그인이 없어 일정은 브라우저별로만 저장됩니다(정책 결정 전 보류).

## 4. 생성형 AI: Anthropic Claude

**선택 이유**

- 구조화 출력(`output_config.format`, JSON Schema)으로 응답을 열거형 값의 JSON으로 강제할 수 있어, "자연어 → 기존 입력 계약의 허용 값" 변환을 서버가 다시 검증하기 쉽습니다.
- 도구 호출(tool use)을 지원해 AI Agent 여행 초안(구현 중)을 같은 API로 만들 수 있습니다.
- 기본 모델은 `claude-haiku-5-5`입니다. 짧은 문장에서 열거형 필드를 뽑는 작업이라 속도·비용을 우선했습니다. 환경변수 `HB_AI_MODEL`(선택)로 다른 Claude 모델로 바꿀 수 있습니다. Agent·RAG 기능이 쓸 모델은 해당 작업 병합 후 AI_DESIGN.md에 적습니다.
- 공식 SDK 대신 공식 문서의 raw HTTP 형식으로 `fetch` 호출합니다. 배포 폴더에 의존성을 두지 않는 원칙(§2)을 지키기 위해서입니다.

**대안과 고르지 않은 이유**

| 대안 | 고르지 않은 이유 |
| --- | --- |
| 다른 LLM 공급자 | 비교 실험은 하지 않았음. 구조화 출력과 도구 호출을 한 API에서 쓰는 구성을 택함 |
| 규칙 기반 파서만 사용 | 자유 문장(예: "서울 근교, 무릎이 안 좋음")을 규칙으로 다 덮기 어려움. 대신 규칙 엔진(추천·일정·접근성 판정)은 그대로 두고 AI는 입력 정리·문장화에만 씀 |

**운영 상태**: 운영 Vercel에 `ANTHROPIC_API_KEY`가 등록되지 않아 AI 기능은 비활성입니다(2026-11-26 `/api/ai-assist` 응답 `{"enabled":false}` 확인). 실제 모델 응답 품질·지연·비용은 확인 안 됨.

## 6. 배포: Vercel

- 문제가 생기면 Vercel에서 이전 정상 배포로 되돌리고 원인 커밋은 revert PR로 고칩니다([GIT_WORKFLOW.md](GIT_WORKFLOW.md)).
- 운영 URL: https://hamkkebom-omega.vercel.app/

## 7. CI·자동화: GitHub Actions + Python

- 노코드 자동화 도구(n8n, Zapier, Make 등)는 쓰지 않았습니다(저장소에 사용 흔적 없음).
- 대신 YAML 설정으로 정의하는 GitHub Actions 워크플로가 실행 시점(PR, main push, 수동)과 경로 조건을 맡고, 실제 처리(데이터 정제, 사진 권리 검사, 공개 동기화 파일 선별, 회귀 검사)는 Python 스크립트가 합니다. 조합 방식은 [PROCESS.md](PROCESS.md) §3에 있습니다.
- Python 스크립트는 대부분 표준 라이브러리만 씁니다(예: `scripts/import_public_toilets.py`). 사진 검사는 격리된 가상환경에서 Pillow, 브라우저 회귀는 Playwright를 설치해 씁니다.
- 선택 이유: 코드·검사·동기화를 한 저장소에서 버전 관리하고, 같은 명령을 로컬에서 재현할 수 있습니다.
- 한계: 비공개 저장소의 Actions 실행은 계정 결제 상태에 따라 시작되지 않을 수 있습니다. 그때는 로컬 실행 결과로 대신 기록합니다.
